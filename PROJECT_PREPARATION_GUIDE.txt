1. PROJECT OVERVIEW & ELEVATOR PITCH (30-SECOND SUMMARY)
================================================================================

"Standard Retrieval-Augmented Generation (RAG) systems use a fixed, one-size-fits-all
pipeline: one static embedding model (like all-MiniLM-L6-v2), one static chunk size
(512 tokens), and a fixed Top-K (k=3). However, different questions demand different
context granularities. Short factoid queries need small 256-token chunks for pinpoint
precision, while multi-faceted questions require larger 512-token chunks and deeper
dense semantic embeddings (like BGE-small-en-v1.5).

Traditional hyperparameter tuning requires human ground-truth answers (ROUGE / BLEU),
which NEVER exist during real-world inference.

In this project, we design and implement REFERENCE-FREE ADAPTIVE RAG. Our system
dynamically selects the optimal retrieval setup per query at runtime using three
intrinsic mathematical signals:
   1. Retrieval Confidence (R)
   2. Semantic Consensus / Uncertainty (1 - U)
   3. Lexical Evidence Grounding (C)

Using a two-stage cascaded architecture with early-exit shortcuts, our Adaptive RAG
improves Token F1 from 43.50% to 47.98% (+4.48%) and Retrieval Hit@K from 84.2% to
88.8% (+4.6%), while maintaining practical interactive latency (~2.7 seconds) without
needing human reference answers or offline re-training."

2. THE PROBLEM STATEMENT: WHY STANDARD (FIXED) RAG FAILS
================================================================================

Fixed RAG systems suffer from three fundamental limitations:

1. THE 'ONE-SIZE-FITS-ALL' RETRIEVAL TRADEOFF:
   - Chunk size 256: Great for exact names, dates, and concise facts, but splits
     complex concepts across chunk boundaries.
   - Chunk size 512: Captures broader context, but introduces irrelevant text that
     distracts the Large Language Model (known as the 'lost-in-the-middle' phenomenon).
   - Top-K = 3 vs Top-K = 5: If K is too small, critical evidence is missed; if K
     is too large, prompt overhead slows inference and increases hallucinations.

2. EMBEDDING MODEL HETEROGENEITY:
   - MiniLM (sentence-transformers/all-MiniLM-L6-v2) is ultra-fast (384-dim), but
     struggles on complex domain jargon.
   - BGE-Small (BAAI/bge-small-en-v1.5) provides superior semantic clustering (384-dim),
     but produces different cosine scale distributions.
   - No single embedding model wins across 100% of queries.

3. THE REFERENCE-FREE DILEMMA:
   - In production, you don't have gold ground-truth answers.
   - You cannot run BLEU, ROUGE, or Exact Match on live queries.
   - The adaptation MUST be self-supervised and reference-free.

3. CORE METHODOLOGY & MATHEMATICAL OBJECTIVE (J)
================================================================================

The router evaluates candidate configurations using a composite objective function:

                  J = (R_norm + (1 - U)_norm + C_norm) / 3

Where:
--------------------------------------------------------------------------------
1. RETRIEVAL CONFIDENCE (R):
   - Definition: The mean cosine similarity of the top-K retrieved text passages.
   - Formula:
        R = (1 / K) * sum_{i=1}^K cos(q, p_i)
   - Interpretation: High R means the vector database found passages that closely
     align with the semantic query vector in latent space.

2. SEMANTIC CONFIDENCE (1 - U):
   - Definition: Agreement across stochastic answer generations at temperature T=0.7.
   - Formula:
        U = 1 - mean_{i < j} cos(E(A_i), E(A_j))
        Semantic Confidence = 1 - U
   - Interpretation: If the LLM generates the same semantic meaning across different
     random seeds, the model is highly certain. If the generations diverge wildly,
     uncertainty (U) is high, indicating conflicting or hallucinated context.

3. EVIDENCE GROUNDING (C):
   - Definition: Token containment measuring the proportion of the generated answer
     that is explicitly anchored in the retrieved text passages.
   - Formula:
        C = mean_{sentence in A} [ max_{p in Passages} ( |tokens(sentence) cap tokens(p)| / |tokens(sentence)| ) ]
   - Interpretation: Penalizes hallucinations. If the generator outputs ungrounded
     claims not present in the context, C drops to near zero.

--------------------------------------------------------------------------------
REFERENCE ISOLATION GUARANTEE:
At no point does the router or generator access reference/gold answers. The dataset
is split into RAGExample (question + corpus) and GoldRecord (reference answers).
Gold answers are stored in sealed storage used strictly by post-hoc evaluation scripts.

4. TWO-STAGE CASCADED ARCHITECTURE (HOW IT WORKS STEP-BY-STEP)
================================================================================

Brute-force Adaptive RAG would evaluate all 8 configurations across all 3 signals,
requiring 24 generator calls and over 60 seconds per query.

Our Two-Stage Cascaded Routing Architecture cuts latency by over 22x:

                    [ User Question + Document Corpus ]
                                     |
                                     v
   +------------------------------------------------------------------+
   | STAGE 1: LIGHTWEIGHT VECTOR PRUNING                              |
   | - Fast vector search across all 8 configurations using FAISS     |
   | - Computes Retrieval Confidence (R) in ~15 ms                    |
   | - Measures intra-family and cross-family margins                 |
   +---------------------------------+--------------------------------+
                                     |
                         [ Early-Exit Decision ]
                                    / \
                                   /   \
           Clear retrieval winner /     \ Ambiguous / Rival match
           (or out-of-corpus)    /       \
                                v         v
   +--------------------------------+   +-------------------------------+
   | FAST EARLY-EXIT (Stage 1 Exit) |   | STAGE 2: PRUNED EVALUATION    |
   | - Triggers if:                 |   | - Prunes hopeless candidates  |
   |   a) Out-of-corpus (R < 0.30)  |   |   (R < 0.30)                  |
   |   b) High confidence (R>=0.55) |   | - Retains top 2 viable rivals |
   |   c) Cross-family lead >= 0.28 |   | - Samples 3 lightweight drafts|
   |   d) Same-spec K-only runner-up|   | - Computes U and C            |
   | - Executes 1 LLM generation    |   | - Picks argmax J              |
   | - Latency: ~1.5 - 2.5 seconds  |   | - Latency: ~3.0 - 4.5 seconds |
   +--------------------------------+   +-------------------------------+
                                     |
                                     v
                        [ Final Grounded Answer ]

5. KEY COMPONENTS & REPOSITORY FILE BREAKDOWN
================================================================================

Root Directory: d:\MyProject\Adaptive_RAG

1. src/cascade.py:
   - Core engine implementing CascadedAdaptivePipeline and CascadedConfig.
   - Contains Stage 1 vector ranking, Early-Exit heuristics, Stage 2 candidate
     filtering, and composite objective J scoring.

2. src/retrieval.py:
   - Implements FaissIndexManager using FAISS IndexFlatIP (Inner Product on
     L2-normalized vectors = exact cosine similarity).
   - Manages indexes for all 8 candidate configurations.

3. src/chunking.py:
   - Implements tokenizer-aware chunking with sliding window and exact token overlap.
   - Guarantees chunk length never exceeds the embedding model context window (256/512).

4. src/generation.py:
   - Implements Phi3Generator wrapping microsoft/Phi-3-mini-4k-instruct.
   - Supports deterministic greedy generation (temperature=0.0) and stochastic
     sampling (temperature=0.7, top_p=0.9) with reproducible random seeds.
   - Uses BitsAndBytes 8-bit quantization to fit comfortably in consumer GPU VRAM (~4.8 GB).

5. src/config.py:
   - Defines CandidateConfig (embedding_key, model_id, chunk_size, top_k, order).
   - Candidate pool: 8 configurations:
       * bge_small_c256_k3, bge_small_c256_k5, bge_small_c512_k3, bge_small_c512_k5
       * minilm_c256_k3, minilm_c256_k5, minilm_c512_k3, minilm_c512_k5

6. app.py:
   - Interactive Gradio Web UI for side-by-side comparison.
   - Displays real-time answers, latency comparison, objective signals (R, 1-U, C, J),
     retrieved passages, and the full candidate routing matrix.

7. tests/ (16 Unit Tests):
   - tests/test_cascade.py: Verifies early exit, stratified family pruning, and lexical containment.
   - tests/test_core.py: Verifies reference isolation, FAISS vector math, and reproducibility.

8. TOP 15 VIVA QUESTIONS & WINNING ANSWERS
================================================================================

Q1: What is the main research objective of your project?
A1: "To solve the one-size-fits-all limitation of standard RAG systems by dynamically
selecting the optimal retrieval configuration (embedding model, chunk size, and top-K)
for each user query at inference time, completely without human reference answers."

Q2: Why is 'Reference-Free' such an important distinction?
A2: "In academic benchmarks, researchers use ground-truth answers to calculate ROUGE
or BLEU scores. But in production, the user is asking a new question whose answer is
unknown. A real RAG system cannot rely on ground-truth references to make retrieval
decisions; it must evaluate its own confidence using intrinsic signals."

Q3: What are the 3 intrinsic signals you use, and how are they combined?
A3: "We compute:
   1. Retrieval Confidence (R): Average cosine similarity of retrieved passages.
   2. Semantic Confidence (1 - U): Agreement across stochastic answer generations.
   3. Evidence Grounding (C): Sub-millisecond token containment of the answer in the chunks.
   We normalize each signal to [0, 1] and maximize the composite score J = (R + (1-U) + C) / 3."

Q4: How did you solve the latency bottleneck of evaluating multiple configurations?
A4: "An exhaustive search over 8 configurations requires 24 LLM calls, taking ~60 seconds.
We solved this with a Two-Stage Cascaded Router:
   - Stage 1 uses fast FAISS vector search (~15ms) to rank all configurations.
   - If the top candidate has high confidence (R >= 0.55), out-of-corpus relevance (R < 0.30),
     or leads rivals by a wide margin (>= 0.28), it triggers Early-Exit in 1 LLM call (~1.5s).
   - Only ambiguous queries advance to Stage 2, where hopeless candidates are pruned,
     evaluating at most 2 viable candidates."

Q5: Why did Adaptive RAG select chunk size 256 more often than chunk size 512?
A5: "Because 512-token chunks often contain extraneous sentences that dilute the attention
of the LLM (the 'lost-in-the-middle' problem). For specific factual queries (like names,
dates, or definitions), 256-token chunks provide a higher signal-to-noise ratio."

Q6: Which embedding models did you use, and why two different families?
A6: "We used sentence-transformers/all-MiniLM-L6-v2 (a fast, lightweight 384-dimensional
model) and BAAI/bge-small-en-v1.5 (a highly accurate 384-dimensional dense retrieval model).
Having both families proves that our router can handle heterogeneous embedding distributions
and pick whichever model best captures the query domain."

Q7: Which LLM generator did you use, and how did you fit it onto a single GPU?
A7: "We used Microsoft's Phi-3-mini-4k-instruct (3.8 billion parameters). To ensure it fits
within 6 GB of VRAM alongside FAISS and embedding models, we loaded it in 8-bit precision
using `bitsandbytes` (quantization_config=BitsAndBytesConfig(load_in_8bit=True)). This
reduced memory consumption from 8.5 GB down to ~4.8 GB without sacrificing answer quality."

Q8: How do you prevent data leakage or 'cheating' during adaptive selection?
A8: "We enforce strict reference isolation at the code architecture level:
   - The query object passed to the retrieval pipeline is an immutable `RAGExample` containing
     only `query_id` and `question`.
   - The gold reference answer is stored in a separate `GoldRecord` structure on disk.
   - Any attempt to access evaluation fields like `gold_answer` or `f1` during routing raises
     an immediate runtime exception."

Q9: How do you measure Semantic Uncertainty (U) without an external LLM judge?
A9: "We generate 3 answer samples using fixed random seeds at temperature T=0.7.
We encode the generated answers into embedding vectors using MiniLM and compute pairwise
cosine similarity. The average pairwise distance is the Semantic Uncertainty (U).
High semantic similarity means low uncertainty (high consensus)."

Q10: What is Evidence Grounding (C) and why not use an NLI Cross-Encoder?
A10: "Evidence Grounding measures whether the facts stated in the answer are actually
contained in the retrieved chunks. Instead of using a slow NLI cross-encoder (which takes
~400ms per passage), we implemented token-level sentence containment that runs in under
1 millisecond. It splits the answer into sentences and computes the maximum token overlap
against retrieved chunks."

Q11: What were the key numerical results from your 500-question benchmark?
A11: "- Token F1 improved by +4.48% (47.98% vs 43.50%).
     - Exact Match improved by +1.60% (20.00% vs 18.40%).
     - Retrieval Hit@K improved by +4.60% (88.80% vs 84.20%).
     - Answer Grounding improved by +11.9% (0.696 vs 0.577).
     - Average latency remained interactive at 2.77 seconds."

Q12: Why does Fixed RAG sometimes fail even when it retrieves the right document?
A12: "Because of static chunking. If the answer lies near the edge of a 512-token chunk,
or if multiple irrelevant paragraphs are retrieved alongside it, the LLM generator can
suffer from distraction or truncate the actual answer. Adaptive RAG dynamically tests
different chunk boundaries and picks the configuration that produces the highest grounding."

Q13: How does your system handle out-of-corpus queries (e.g. '2 + 2 = ?' or unrelated topics)?
A13: "Stage 1 checks the maximum retrieval confidence. If top_r < 0.30 (min_relevance_threshold),
the system recognizes that the corpus contains no relevant evidence. It triggers the
Low-Relevance Shortcut, executing a single fast generation (~0.5s) to state that the context
does not contain the answer, rather than wasting 6 sampling calls on noise."

Q14: What vector search algorithm do you use in FAISS?
A14: "We use `faiss.IndexFlatIP` (Flat Inner Product). Since all query and passage embeddings
are L2-normalized upon creation, the inner product is mathematically identical to exact
cosine similarity, ensuring 100% precision with zero vector distortion."

Q15: What are the future enhancements for this project?
A15: "1. Adding asynchronous parallel retrieval across configurations.
     2. Supporting hybrid retrieval (combining dense vector search with sparse BM25 keyword search).
     3. Implementing dynamic speculative decoding for even faster LLM generation."

9. KEY TECHNICAL TERMS CHEAT SHEET
================================================================================

* RAG (Retrieval-Augmented Generation): Enhancing LLM generation by retrieving relevant
  external documents from a vector database before generating the answer.
* Embedding: A dense numerical vector representation (e.g. 384 numbers) of text that
  captures semantic meaning.
* FAISS (Facebook AI Similarity Search): High-speed vector database library for dense
  vector similarity search.
* IndexFlatIP: Exact FAISS index computing inner products (cosine similarity on normalized vectors).
* Chunk Size: The maximum number of tokens contained in a single split text passage (256 or 512).
* Top-K: The number of highest-scoring passages retrieved and provided to the LLM context.
* BitsAndBytes (8-bit Quantization): Compressing 16-bit floating-point neural network weights
  into 8-bit integers, halving GPU memory usage while retaining full model accuracy.
* Early-Exit: An algorithmic shortcut that skips expensive downstream pipeline stages when
  the initial stage produces an unambiguous winner.
* Token F1: The harmonic mean of token-level precision and recall between the predicted answer
  and the ground-truth text.
* Exact Match (EM): A strict metric equal to 1.0 if the predicted answer matches the target
  character-for-character, and 0.0 otherwise.
* Hit@K: Percentage of queries where at least one retrieved chunk contains the required answer text.
* Hallucination: When an LLM generates convincing-sounding statements that are not supported
  by factual evidence.
